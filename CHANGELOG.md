# Changelog

All notable changes to `@isokron/mcp-check` and the `isokron-ai/mcp-check` Action. The package follows [semantic versioning](https://semver.org/); the grading rubric has its own version (`rubric_version`), noted with each release.

## 1.2.0 (unreleased)

### Rubric 2.2.0

The write surface is reported as guard coverage, not as a letter, and four checks read less into names and arguments. No weight, band or cap changes for the five graded sections. The full list is in [RUBRIC.md](RUBRIC.md), "Changes in rubric 2.2.0". The web checker needs the same engine to stay in step.

**Breaking output change.** The write surface has no grade any more: `sections.surface.grade` (and `score`) are always `null` in the JSON report, the MCP server's `check_tools_list` and the corpus records, and `badge.json`'s `grades` object no longer has a `surface` key. A workflow or dashboard that read the write-surface letter gets nothing to compare; read `sections.surface.coverage` instead.

**Reading the JSON.** `sections.surface` keeps its shape: `grade` and `score` are now always `null` (as they already were for a server with no write tools), so a consumer that reads `sections.surface.grade` gets `null` and should treat it as "not graded". New fields: `graded: false`, `state` (`coverage`, `not-enough` below 3 guard opportunities, `no-opportunities`, `no-writes`), `coverage` (`opportunities`, `offered`, and `{ have, of }` for `retry`, `version` and `guard`), `summary` ("Guards offered: retry keys 0/19, preconditions 3/53, delete guards 0/8."), `skipped` (session and HTTP-client tools left out) and, on each part, `short`. `parts` and `rows` are unchanged in shape; rows may now have the kind `session` or `http client`. The surface findings `surface-retry-key`, `surface-version-guard` and `surface-bulk-delete` are `advice` (they were `attention`), so their SARIF level is `note`. The badge file's `grades` no longer has a `surface` key. The Action output `grade-surface` stays and is always empty.

- **Write surface: no letter.** It counts the guards the write tools offer, pooled ("Guards offered: retry keys a/b, preconditions c/d, delete guards e/f"), says "not enough to judge" with fewer than 3 opportunities, and lists per-tool advice. It is left out of the CLI text report's grade lines, the job summary's grade table, the PR comment, the badge and the Action's log line. Selecting `surface` in `--sections` (or the Action's `sections`) adds one coverage line under the grades; `--min-grade` never gates it, and the CLI and the Action say so when both are set. The Markdown export and `report.md` keep the full write-surface section. The MCP server's `check_tools_list` keeps a `surface` entry with a null grade, its coverage in `note`, and new `state` and `coverage` fields.
- **Write-surface detection**: argument names are read in words and one level down (`expectedHeadSha`, `ops[].expect_version`); `force` and `allow_*` are not delete guards; `merge_request_id` is not a retry key and `new_version` not a precondition; `confirm_token`, `expect(ed)_*`, `base_(sha|revision|version)`, `if_match`, `etag` and `last_modified` are preconditions; `validate_only`, `dry_run` and `confirmation_text` are guards; `create_or_update_*` is an upsert judged by its precondition; session tools (in a browser list, only tools whose own name is a browser action, prefix or noun; page, element and extension only with a browser verb such as close or uninstall) and HTTP clients (`http` or `request` in the name, or `client` before a method as in `client_put`, with a `url`) are not counted; `surface-full-replace` needs every field required and stays quiet with a precondition, a patching sibling, a find-and-replace or an HTTP client.
- **Verbs** (every check that reads a name): after a namespace prefix, a verb that is never a noun wins over a last word that is a write verb but usually a noun there (`acme_get_issue_comment` reads, `idp_create_application_grant` creates); it does not apply after query, view, list, set, patch or show, before and/or/then, in a find-and-replace or over a delete, so `pg_query_cancel` and `db_view_drop` stay deletes and no 2.1.1 write becomes a read except such gets; `hide`, `unhide` and `supersede` update; `disable_*` updates, so `annot-delete-marked-safe` no longer fires on it; `tombstone` and `retire` delete; `append`, and a leading `record` or `checkpoint`, create; whole-name data-store reads (`hget`, `lrange`, `smembers`, `dbsize`) read; `type`, `keys`, `scan` and `exists` do not.
- **`anthropic-hint-platforms-differ`** is not raised for creates led by create, add, insert, append, record, new or comment that purely add. Other creates (send, pay, charge, transfer, publish, deploy, share, invite, import, schedule, copy, upload) keep it, and so do additive-led names whose object moves money, sends or ships (`create_refund`, `create_message`, `create_deployment`, `create_and_send_invoice`).
- **`openai-retry`** is raised only for tools read as writes (named as a create, update or delete, or with an unclear name and no `destructiveHint: false`); a word on retries in an argument's description, or a retry-key argument, counts.
- **`openai-restricted-input`** also reads the fields of an object or array argument (`person.ssn`), and keeps a credential name on the container unless every field is a setting (a `refresh_token` settings object is no longer blocking; `cookies: [{ name, value }]`, `password: { value }` and a `credentials` object still are).
- **`openai-precise-location`**: coordinates are blocking only when the text points at the user's own location ("your current location", "near me", "nearby", "where I am"); otherwise attention (a place to search, an emulated device position, a clause that says not to ask, such as "Do not ask for the user's location").
- **Poisoning**: a hyphen- or underscore-joined run of three or more words inside prose ("Note: always-call-this-tool-first before anything else.") is also read as words for instructions, hard steering and outside instructions. No new findings on the test catalogs or the calibration set.
- **Tests**: both sides of every change in `test/calibration.test.cjs` ("2.2.0" tests); CLI, Action and PR-comment output in `test/cli.test.cjs`, `test/action.test.mjs` and `test/action-zero-config.test.mjs`.

- **Linear reading of hyphen-joined words in prose.** The pattern that reads "always-call-this-tool-first" as words now starts only at the beginning of a word, so a very long word in a description no longer takes seconds (an 80 KB word: 3.5 s before, under 10 ms now). Three older patterns get the same treatment: the camelCase split of names (a long run of capitals), the `# system` markup check (many newlines) and the printable test of decoded base64; a 2 MiB string in any field now takes under 2 s, where these could take from minutes to hours. They were also in 1.1.1 and the web checker. Findings are unchanged.

### Reading source

`--repo`, `--repo-dir`, `--registry` (when it falls back to the source) and the zero-config Action read far more of a server's tools from its source, and no longer grade what they cannot read. No rubric change in this part; the engine is not changed.

**Behaviour changes.** Many repositories that gave "no tool definitions found" (exit 3; a neutral Action run) now give a list and are graded (exit 0 or 1). Grades can move, mostly up: checks of a schema, description or annotations the reader cannot work out are skipped instead of graded as empty. A Go or Rust repository still exits 3 (a neutral Action run), but the message now lists the tool names it read. `--repo` with a subfolder lists only that folder's tree. The `Source:` line of a committed-snapshot union names it as every toolset and flag variant.

- **Tool names held in identifiers (TypeScript and JavaScript).** A name is read from a string constant of the file, a constant imported from another file of the repository (followed through re-exports, `export *` and path aliases such as `~/`, `@/` and workspace packages), a member of a constant object or enum (`TOOLS.SEARCH`, `dataTool.name`), a template or `+` of constants, and `name || "default"`. A registration whose name still cannot be read is not guessed: the `Source:` line counts it ("N registrations with a name the reader could not resolve").
- **More TypeScript registration forms.** A config held in a constant (`registerTool(name, config, …)`); helpers named like a tool call (`context.scopedTool("x", { description, inputSchema })`, `defineTool`, `createTool`, `tool`) when given a name and a config with a description, schema, title or annotations; tool objects returned by a factory (`defineTool((args) => ({ name, description, schema }))`) whatever their description; keyed tool tables (`{ lookup_docs: tool({ ...defs.lookup_docs, execute }) }`, named by the key); `Object.freeze({ name, inputSchema })`; and classes whose base class registers `this.name` (`class MeasureTool extends BaseTool { name = "measure_tool"; … }`, `static toolName = "lookup"`), grouped with the package that registers them; such classes in test, mock or example folders are not tools.
- **zod and schemas.** zod is found by its import binding, also when the repository re-exports it (`import { zod } from "../lib/schema"`). A raw zod shape held in a constant is wrapped as the SDK wraps it; a shape with a property named `type` is a shape, not a schema; zod constants with more calls (`Param.optional().describe(…)`), `z.preprocess`, `z.coerce`, `z.toJSONSchema(X)` and `discriminatedUnion` are read; values ended by a line break without a semicolon are read.
- **Python: the FastMCP decorators in general.** Comments inside decorators and signatures no longer hide a tool. Any `@<server>.tool(...)`; names from string constants, module constants (also imported ones), `Enum` members (`Tools.STATUS.value`), f-strings and implicit concatenation; project decorators named like one (`@acme_tool(description=…)`); methods of the repository that register a tool, used as decorators (`@registry.reader("Read notes")`); `mcp.tool(fn, name="…")`, `add_tool(fn)`, `Tool.from_function(fn)` and `*ToolDefinition(fn=…)`. Under Python SDK 2.x, snake_case `ToolAnnotations` fields are listed in camelCase, as that SDK sends them.
- **Python low-level servers.** `Tool(name=…, description=…, inputSchema={…}, annotations=…)` and `types.Tool(...)` are read, with `name=self.name` taken from the handler class's `super().__init__(…)`.
- **FastMCP composition.** Tools of a server mounted with `mount(child, namespace="issues")` (or `prefix=`, or `mount("issues", child)`) or `import_server("issues", child)` are listed as `issues_<name>`, as FastMCP lists them. `alternate-server` (one of several modules picked by configuration) now applies only when a module repeats at least half of its names in the kept one, so two modules that share a function name or two are both read.
- **Not readable is not graded.** When a tool's input schema, description or annotations cannot be worked out statically (built at run time, a function call, set by a base class), the reader notes it, and only for a list this run read from source (`--repo`, `--repo-dir`, `--registry` falling back to source, the zero-config Action) are the checks of that part skipped for that tool; the sections are graded on the rest with the rubric's weights, bands and caps. The note comes from the reader's own result, never from the list: a schema that still has properties is always graded. An unreadable schema is written as `{"type": "object", "x-mcp-check-unknown": true}` (also by `--save`), but that marker is not trusted on input: grading a saved file, stdin, a live server, a tools-file or `check_tools_list` grades the schema as given. Text, Markdown, JSON (`skipped_checks`), the job summary and the PR comment say how many parts were not readable and how many checks were skipped ("Not readable from source: 3 input schemas, 1 description; 12 checks of those parts skipped"); `source.unreadable` names the tools. If the rubric's grading cannot be reproduced to skip them, nothing is skipped and the report says so. A tool whose schema is not readable is left out of the write-surface coverage counts (its guards are unknown), rather than counted as unguarded, and the section names them ("1 write tool with an unreadable schema not counted (…)"). The readable string parts of an unreadable description (`d('…')`, `[…].join(' ')`) are kept as its text, so the poisoning checks still read them; a description read in part shows the unread part as `…`.
- **Nothing read from source is dropped silently.** Whatever the reader cannot place in a tool (a value it cannot read, such as a function call or a value nested deeper than 70 levels, or the part of a string past 64 KiB) has its text kept: it is scanned for hidden instructions as part of that tool, and the report counts the tools concerned ("N tools with source the reader could not read in full: that text was scanned"; `source.unreadable.text` names them). Values up to the 64 levels a tool list may have are read in full; a list nested deeper is refused by the list limit, as before.
- **Registrations whose name cannot be read** are not listed (the `Source:` line counts them), but their description and title are still scanned for hidden instructions; a blocking finding counts against the list (security, Anthropic and OpenAI F).
- **One bad registration never hides the others.** Strings built from constants are capped at 64 KiB (longer is partial and not readable), and a registration the reader fails on is counted as unresolved instead of dropping the rest of its file. Brackets are matched in one pass and every object and array of a file is read once, innermost first, so deeply nested source is read in time linear in its size and nesting before or between tools never uses up the reader's work limit. If that limit were ever reached, or the reader fails on a registration, the list is refused (exit 3; a neutral Action run) rather than graded incomplete.
- **Which literals count (D4).** A literal tool object counts where code hands it on (an argument, an array element, a return value, an arrow's result) or where it is bound to a constant that something refers to; a `{ name, description, inputSchema }` constant nothing refers to is left out, as before.
- **Conditions and deprecation.** A tool that declares conditions is kept (marked) when every condition names an option the source declares with `default: true`. A tool definition that flags itself `deprecated` is left out (`deprecated-flag`), as servers with such a flag drop it from the list. `mocks` folders are skipped like `__mocks__`.
- **More files, read by content.** Source files are taken by likelihood and then path, as before, but the limit is no longer 60: up to 1,500 are read, and the first 400 whose text may define a tool (a cheap content test) are read for tools; the others lend their constants. Reading stops at 64 MiB in all for one scan (files over the 1.5 MiB cap are skipped before download), and the message says so. The no-tools message says how many were read and when a limit was hit.
- **No partial lists from GitHub.** When GitHub refuses or fails any file read of a `--repo` scan (a rate limit, a server error), nothing is graded: exit 3 with "GitHub rate limit: N file reads failed (HTTP 429 …); retry later, pass a token (--github-token-env), or read a checkout with --repo-dir".
- **Subfolders of large repositories.** `--repo github.com/o/r/tree/<ref>/<folder>` lists that folder's own tree, so GitHub's cut-off of a large repository's listing no longer hides it; a listing GitHub cut short is named in the message, with the advice to point at the server's folder.
- **Go and Rust names.** In a Go or Rust repository with nothing else to grade, the tool names and descriptions are read (mcp-go `mcp.NewTool("x", mcp.WithDescription("…"))`, the go-sdk's `&mcp.Tool{Name: "x"}`, `MustTool("x", "…", …)`, rmcp `#[tool(description = "…")] fn x`) and the refusal lists them: "names and descriptions only, since Go schemas are not read yet". Nothing is graded on names. C# is not read yet.
- **One list in any listing order.** Committed `__toolsnaps__` files of equal path length are taken in path order, so `--repo` and `--repo-dir` give the same catalog hash.
- **Tests**: `test/repo-reader-patterns.test.mjs`, one synthetic source per pattern above, plus a check that the regrade reproduces the engine's grades on every test catalog.

## 1.1.1 (2026-11-20)

A patch: reading a server from its source gets safer. Grades read from source are labelled approximate, the Action no longer fails a job it cannot grade, monorepos are no longer merged or guessed, and two poisoning heuristics stop firing on identifiers. Rubric 2.1.1 (the poisoning change below; no weight, band or cap changes). The web checker needs the same engine edit to stay in step.

**Behaviour change in 1.1.1.** In the Action's zero-config mode, a repository that gives nothing to grade (no tool definitions, names only, or more than one server) no longer fails the job: it ends with a warning, and the `passed` output is empty instead of `false`. A workflow that relied on that red job (for example to require a gradable list) should set `fail-on-no-tools: true`. Workflows with `command` or `tools-file` are unchanged.

- **Static reads are advisory.** A list read from source code (`literal` or `derived`, in the Action's zero-config mode and in `--repo`, `--repo-dir` and `--registry` when they fall back to the source) is labelled "approximate: read from source, not the server's live list": in the job summary heading and note, the PR comment heading and source line, and the CLI's text and Markdown reports (and `source.approximate` in JSON). Each says to use `command` / `tools-file` (`--command` or a saved list) for exact grades. Exact committed lists and snapshots are not labelled. The Action never fails on grades unless `min-grade` is set; when it is set on approximate grades, the summary and log say the gate is at the user's own risk. New Action output `approximate`.
- **No red job when there is nothing to grade.** With neither `command` nor `tools-file`, when the source gives no list to grade (no tool definitions, including Go, Rust and C# servers whose source is not read yet; a manifest with names only; or tools of more than one server), the Action ends neutral: a `::warning::`, a job summary headed "not graded" with the fix, exit status 0 and an empty `passed` output. With `pr-comment` on, the pull request's comment is updated to "not graded on this run" (`auto` updates an existing comment only; `always` makes one), so an earlier verdict does not stay up. New input **`fail-on-no-tools`** (default `false`) restores the old failure. The message names the language when the source is mostly Go, Rust, C#, Java, Kotlin, Ruby, PHP or Swift.
- **Names-only lists are never graded by the CLI either.** `--repo`, `--repo-dir` and `--registry` exit 3 on a manifest that lists tool names without schemas, with the same advice as the Action.
- **Several servers are not merged or picked.** Tools are grouped by package (the nearest folder with a `package.json`, `pyproject.toml` or `setup.py`), and a package that constructs a server (`new McpServer`, `new Server` from the SDK, `FastMCP(...)`) is noted. Only when two or more packages each construct a server and have tools is nothing graded: the CLI exits 3 and the Action ends neutral, both listing the package folders (server constructors first) to point `--repo-dir`, `--repo …/tree/<ref>/<folder>` or `working-directory` at. A monorepo with one server is still graded: packages with a constructor and no tools (a test stub) are dropped; a single package that only holds SDK registrations (its tool library) is graded with the one server (two or more such packages may be other servers, so the repository is not graded); packages with only bare tool literals and no server (a client's tool table) are set aside. Folders named `admin`, `console`, `docs`, `evals`, `examples`, `fixtures`, `tests`, `bench`, `e2e`, `playground`, `demo`, `samples`, `mocks`, `site` or `website`, and folders with such a word in their name (`docs-mcp`) when another package constructs a server, are set aside and their tools listed as left out; they are graded when pointed at directly. Of several committed tool lists, the one nearest the root (or the only one inside the server's package) is used, and the report names the others; when none stands out, none is used. The `--compare` file is never read as the list, as the Action's `baseline` already was not.
- **More folders skipped when reading source**: `eval`, `evals`, `bench`, `benches`, `benchmark(s)`, `e2e`, `__mocks__`, `playground` and `website`, beside tests, examples, docs and fixtures. An evaluation harness's tool literals are no longer read as the server's tools.
- **Poisoning: fewer false positives, no new blind spots (rubric 2.1.1).** `sec-secret-seeking` needs a space after the verb, so a short identifier such as a hyphenated event name containing "password" no longer reads as a request for one ("upload the db-credentials" still does). A `.env` file named without the model being asked to read, copy or send it is attention, not blocking; only a tool whose name says it saves or writes a file (`save_settings_to_file`, `write_env`) may read the file it updates, and reading `.env` and copying it into something, or sending it, is blocking for every tool. Short identifiers (at most four segments joined by `.`, `_` or `-`, such as enum values and event names) are not read as asking for secrets or as soft steering, but are still read for instructions, hard steering and outside instructions, so an enum value `ignore-previous-instructions` stays blocking. The phrase checks read blank and invisible characters (U+2800, U+3164, U+FFA0, zero-width) as spaces and longer hyphen- or underscore-joined runs as words, so "Ignore-all-previous-instructions" and enum values written as sentences are still caught. `.env` after `/` (`./.env`) and the gcloud `application_default_credentials.json` file are now recognised. SSH keys, cloud credential files and MCP client configuration stay blocking wherever they appear. Tests on both sides in `test/calibration.test.cjs`, including every review probe string.
- **Wording**: the registry line in the job summary and PR comment, the README and the Action docs no longer speak of a "CI-verified grade"; the line now says the server can be listed in the IsoKron MCP registry (beta), with a public page of its grades.

## 1.1.0 (2026-11-20)

New inputs and a new option, so a minor version; it also carries the changes first planned for 1.0.1, further down. The rubric stays 2.1.0. The engine changes in two heuristics (below); both can only remove advice-level findings. The web checker needs the same two edits to stay in step.

- **Zero-config Action.** With neither `tools-file` nor `command`, the Action reads the tool definitions from the source in `working-directory` and runs nothing. The job summary says so ("Source: repository code; nothing was run"), names how exact the list is, and says how to switch to the live list with `command` or `tools-file`. SARIF results point at the line that registers each tool. When no tool definition is found the job fails with that advice. New output `source` (`repo-static`, `command` or `tools-file`). The smallest workflow is now `actions/checkout` followed by `uses: isokron-ai/mcp-check@v1`.
- **`--repo-dir <path>`**: the `--repo` reading from a local checkout, with no network access. It does not enter `node_modules`, `.git`, virtual environments or caches, does not follow symlinks, keeps `--repo`'s limits (60 source files, 1.5 MiB per file), and reads build output (`dist`, `build`, `out`) and `vendor` only when no source file defines a tool. Exit code 3, with a message naming `--command` and a saved list (`command` and `tools-file` in the Action), when it finds no tool definition. Library: `RepoSource.fromDirectory(path)` beside `fromGitHub`, sharing one scan.
- **The source reader follows same-file helpers** that pass a name and a config on to `registerTool`, such as `function register(server, name, config, fn) { server.registerTool(name, config, wrap(fn)); }`, in `--repo`, `--repo-dir` and the Action. This package's own server registers its tools that way.
- **`publish-hint`** (default `true`): on a public repository on github.com, the job summary ends with a link to the repository's page in the IsoKron MCP registry, where it can be listed for free with its CI-verified grade and a README badge. It is a link only; no request is made. Private repositories, GitHub Enterprise Server and events without a public repository in their payload get no line.
- **`pr-comment`** (`off` by default; `auto` or `always`) and **`github-token`**: one comment per pull request, found again by a hidden marker and updated in place, with the grades, the gate, a high-risk annotation change, the first five findings linked to their check pages, and the registry line. `auto` comments only when a gated section is below `min-grade` or the baseline comparison finds a high-risk change, and then keeps an existing comment current. Pull requests from forks are skipped, with a note in the job summary. The comment is written by its own step, the only one that receives the token (the server `command` starts never has it in its environment); that step reads the pull request from the event payload rather than from the run step's outputs, runs with a clean environment and the `node` found before any repository code ran, and edits only a comment written by the token's own account, so a marker comment by someone else is never taken over. The body carries the run id and attempt, and the comment step posts only a body from the same run and attempt (a leftover body from an earlier run is also deleted first thing). New input **`pr-comment-key`** gives each job or matrix leg its own comment. Text from the tool list cannot @mention anyone. A failure to comment is a warning and never fails the job. Needs `permissions: pull-requests: write`. Its links carry the new tag `utm_source=mcp-check-pr-comment&utm_medium=action`.
- **Committed lists in zero-config are labelled, and the baseline is never one.** When the Action grades a committed list (`tools.json`, `tools-list.json`, `mcp-tools.json`, `__toolsnaps__`, `.mcp-catalog/`) instead of code, the job summary says first that it graded that file, not the code, and that it may be stale; SARIF points at the tool's line in it. The `baseline` file is excluded from the scan (and refused if it were chosen), so a change in code is compared with the baseline instead of the baseline with itself. A manifest with names only (no schemas) is not graded in the Action: the job fails and asks for `command` or `tools-file`. A folder over the 20,000-file listing limit is read likely source folders first (`src`, `lib`, `server`, `app`, `packages`, ...), then breadth first, and the summary and the `Source:` line say it was cut. SARIF paths are percent-encoded.
- **`--repo` and `--repo-dir` read the same files**: source files are taken by likelihood, then by path, whatever order the listing came in.
- **mcp-catalog-snap snapshots** (`.mcp-catalog/<server>.json`, written by [mcp-catalog-snap](https://github.com/isokron-ai/mcp-catalog-snap)) are read as an exact committed list by `--repo`, `--repo-dir` and the zero-config Action when the snapshot's `server.name` is the repository's own server name (from the server's constructor, `package.json` or `pyproject.toml`; no case, scope or `mcp-`/`-mcp` affix). A snapshot of another server is never chosen over tools read from source; with none, a single one is used and labelled as possibly not this repository's server, and several are not used. The Action's `baseline` accepts a snapshot.
- **`test/`, `tests/` and `__tests__/` are skipped** for committed lists too (source files there were already skipped), in `--repo`, `--repo-dir` and the Action.
- **A server started by `command` (CLI and Action) no longer gets `GITHUB_ENV`, `GITHUB_PATH`, `GITHUB_OUTPUT`, `GITHUB_STATE` or `GITHUB_STEP_SUMMARY`** in its environment.
- **CI**: a `zero-config` job runs the Action with no inputs on this repository, exactly as the docs show.

- **`--repo` reproduces the SDK that the repository pins.** The reader detects the TypeScript SDK line (1.x or 2.x) and the schema library (zod 3 or 4) from the manifests and lockfiles, and the Python SDK or standalone `fastmcp`, and emits what that combination lists: JSON Schema dialect, open or closed objects, integer bounds, titles, `<fn>Arguments` wrappers and `_meta` as the SDK adds them. `execution.taskSupport` is added only for TypeScript SDK 1.24 to 1.x, no longer for every repository. Without detectable SDK information the output has no `execution` field.
- **`--repo` reads more schema forms**: object spreads of local and shared constants, `.shape`, `.optional()` on constants, string and integer constraints in Python annotations and `Field(...)`, docstring `Args:` sections, and placeholders for properties it cannot read instead of dropping them.
- **`--repo` leaves out tools that the server would not list.** A tool is set aside when a literal table disables it, when it declares run-time conditions, when it exists only in one of several alternative server modules, or when it is a declaration that nothing registers; tools registered under a condition that cannot be decided from source are kept and marked. The `Source:` line says how many were left out, why, and how many were kept under a condition. If every tool would be left out, none is.
- **Engine**: `annot-write-marked-readonly` treats `open_` followed by an existing object (`open_nodes`, `open_file`) as a read; `open_pull_request` and `open_issue` still create. `surface-full-replace` no longer counts `move_`, `rename_`, `assign_`, `unassign_`, `transition_`, `merge_`, `restore_` and `sync_` as replacing a whole object when all their arguments are required, since those take two operands or one state change. Tests in `test/calibration.test.cjs`.
- **Tests**: `test/repo-reader.test.mjs` covers the reader on synthetic repositories; `test/checks.test.cjs` already pins that a live answer without `resultType`, `ttlMs` and `cacheScope` is `advice` for a 2025-11-25 era server and `attention` only when the answer carries 2026-07-28 fields.

## 1.0.0 (2026-11-19)

Rubric 2.1.0, MCP specification 2026-07-28, directory rules as read on 18 November 2026.

First public release: the engine of the [isokron.ai/mcp-check](https://isokron.ai/mcp-check?utm_source=mcp-check-readme&utm_medium=readme) web checker as a package, a command line, an MCP server and a GitHub Action, at one version.

- **Engine**: 76 checks with stable IDs in six sections (MCP spec, Anthropic directory, OpenAI directory, poisoning and hidden text, schema and description quality, write-surface design), each with its source quoted verbatim, an explanation and a fix. Per-section grades A to F from severity-weighted deductions with published bands and caps ([RUBRIC.md](RUBRIC.md)). JSON Schema 2020-12 validation with the bundled Ajv 8.17.1. Safe-fix list, SHA-256 definition hashes and a diff that flags high-risk annotation changes.
- **CLI** (`mcp-check`): text, Markdown, JSON and SARIF output; `--min-grade`, `--sections`, `--fix`, `--compare`, `--stdin`, `--sarif-uri`, `-o`. `mcp-check serve` runs the MCP server.
- **Inputs**: `--url` (Streamable HTTP, 2026-07-28 stateless and the earlier handshake, SSE, paging; `--header` values read from the environment and never printed), `-- <command>` / `--command` (stdio), `--config auto|<file>` (Claude Desktop, Claude Code, Cursor, Windsurf, VS Code JSONC, Zed), `--repo` (static extraction with a provenance label), `--registry`, `--save`, a `Source:` line on every report, exit code 3 when a server cannot be reached. Every path sends `initialize` and `tools/list` only and keeps the size, page, time and output limits.
- **MCP server** (`mcp-check serve`, `mcp-check-server`): `check_tools_list`, `explain_check`, `compare_tools_lists`, all read-only with output schemas; input limits of 2 MiB, 64 levels and 2,000 tools. Grades A in every graded section against itself. Registry name `io.github.isokron-ai/mcp-check`.
- **GitHub Action** (`isokron-ai/mcp-check@v1`): a tool-list file or a server command; job summary with the grade table; reports artifact; SARIF with file locations and optional code-scanning upload; minimum-grade gate; baseline comparison; README badge as a shields.io endpoint file committed to the user's repository.
- **Hardening**: job-summary text from the list or the server is escaped so it cannot form links, images or HTML; the Action never reads or writes through a symlink and writes only into a results folder it made; the server's stderr is fenced with `::stop-commands::`; the 2 MiB, 64-level and 2,000-tool limits apply in the CLI and the Action too.
